===== HOOK =====

Large language models are trained on public data.
They do not know about YOUR documents.

Your company wiki.
Your research papers.
Your private data.

So how do you get an LLM to answer questions
about content it has never seen?

That's where RAG comes in.


===== WHAT IS RAG? =====

RAG stands for Retrieval-Augmented Generation.
You retrieve relevant pieces at query time
and include them in the prompt.

[SHOW: Diagram 1 - Documents Don't Fit]

Here's the problem RAG solves.

LLMs have a context window.
That is the limit on how much text they can see at once.

You can't just paste your entire document library into the prompt. It won't fit.

[SHOW: LangChain4j indexing diagram]
https://docs.langchain4j.dev/tutorials/rag

So here's how RAG works:

One. Load your documents.
PDFs, web pages, whatever.

Two. Chunk them into smaller pieces.
We cannot fit entire documents in a prompt.

Three. Embed each chunk.
Convert it to a vector that captures meaning.

Four. Store those vectors in a database optimized for similarity search.

[SHOW: LangChain4j retrieval diagram]

Five. When a user asks a question,
retrieve the most relevant chunks.

Six. Generate an answer by sending the question plus those chunks to the LLM.

The LLM sees your data in the prompt context, not in its training.

That's the key insight.


===== WHAT ARE EMBEDDINGS? =====

[SHOW: Diagram 4a - Embedding Space Clustering]

Now let's make embeddings concrete.

Embedding turns text into a vector.
A vector is just a list of numbers.
It captures semantic meaning.

Similar meanings end up near each other in vector space.

Apple and banana are close.
Chicago and Detroit are close.
Dog and cat are close.

[SHOW: Diagram 4b - Query Vector Finding Matches]

When someone asks a question, it gets embedded too.

A question about fruit lands near the fruit cluster.
RAG finds the nearest chunks and retrieves them.

That's how the system finds the most relevant pieces of your documents.


===== WHY DOES RAG EXIST? =====

[SHOW: Diagram 2 - Context Window Timeline]

RAG started when context windows were tiny.
Think 4K or 8K tokens.

Today, context windows are much larger. So do we still need RAG?

For now, yes.
Some models now support up to 1M tokens.
That is impressive.
But the question shifts from "can it fit?"
to "should we send all of it every time?"

Caching can lower long-context cost.
But it does not eliminate cost.
And cache hits drop when prompts,
users, or documents vary.

Your data also changes over time.
Cached context can go stale.
RAG retrieves fresh, relevant chunks at query time.
That improves precision, cost, and traceability.

This is worth watching.
The original constraint is shrinking.

With that foundation in place,
let's run the three implementations.

===== CODE WALKTHROUGH =====

[CHAPTER: Side-by-side code comparison]

[SHOW: Side-by-side of all three: document_loader.py, DocumentLoaderService.java, DocumentLoader.java]

All three versions follow the same six-step flow.
The differences are in the wiring.

For chunking:
Python uses `RecursiveCharacterTextSplitter`.
It usually keeps paragraph-friendly boundaries.
Spring AI uses `TokenTextSplitter`.
It is token-based splitting.
LangChain4j uses recursive splitting with character overlap.

Different strategies, same goal:
chunks small enough for prompts,
large enough to stay useful.

[SHOW: Diagram 3 - RAG Retrieval Flow]

[SHOW: rag_chain.py, RagService.java (Spring AI), RagService.java (LangChain4j)]

For retrieval and generation:
Python chains components with LangChain expression language.
Spring AI uses `ChatClient` with `QuestionAnswerAdvisor`.
LangChain4j uses `AiServices`:
define a Java interface,
and it generates a proxy.

Three APIs, same pattern.


===== THE PROMPT TEMPLATE =====

[CHAPTER: Prompt behavior and guardrails]

All three frameworks provide sensible defaults:
answer based ONLY on this context.
If the answer is not there, say so.

This reduces hallucinations
by constraining the model to retrieved context.

You can customize prompts,
but defaults are good for most use cases.


===== BONUS: PERSISTENT STORAGE =====

[CHAPTER: Production-style persistence]

[SHOW: Supabase dashboard]

The main branch uses in-memory storage.
Great for demos.
But vectors disappear when the app stops.

On a separate branch, I added Supabase:
PostgreSQL with the `pgvector` extension.

Key point:
all three implementations connect to the same database
and share the same table.

[SHOW: Schema diagram]

I aligned the schemas:
same table name,
same embedding model,
same metadata format.

Load from Spring AI.
Query from LangChain4j or Python.

This took deliberate configuration.
Same database does not mean automatic interoperability.
You must align table structure,
embedding dimensions, and metadata format.

Once aligned, cross-language interop is powerful.


===== WHEN TO USE RAG =====

[CHAPTER: Decision guide]

Use RAG when your data changes frequently.
No retraining needed.

Use RAG when you need citations.
You know exactly what the model saw.

Use RAG when data is private
and you need strict control
over what context is retrieved.

Fine-tuning is expensive.
Changing model weights can make behavior harder to predict.

RAG is transparent.
You can inspect retrieved chunks
and debug wrong answers directly.

For many enterprise use cases,
RAG is the right starting point.
