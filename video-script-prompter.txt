===== HOOK =====

Large language models are trained on public data—they don't know about YOUR documents.

Your company's internal wiki, your research papers, your private data.

So how do you get an LLM to answer questions about content it's never seen?

That's where RAG comes in.


===== WHAT IS RAG? =====

RAG stands for Retrieval-Augmented Generation.

Instead of training or fine-tuning a model on your data—which is expensive and slow—you retrieve relevant pieces of your documents at query time and include them in the prompt.

[SHOW: Diagram 1 - Documents Don't Fit]

Here's the problem RAG solves.

LLMs have a context window—a limit on how much text they can see at once.

You can't just paste your entire document library into the prompt. It won't fit.

[SHOW: LangChain4j indexing diagram]
https://docs.langchain4j.dev/tutorials/rag

So here's how RAG works:

One. Load your documents—PDFs, web pages, whatever.

Two. Chunk them into smaller pieces, because we can't fit entire documents in a prompt.

Three. Embed each chunk—convert it to a vector that captures its meaning.

Four. Store those vectors in a database optimized for similarity search.

[SHOW: LangChain4j retrieval diagram]

Five. When a user asks a question, Retrieve the most relevant chunks.

Six. Generate an answer by sending the question plus those chunks to the LLM.

The LLM sees your data in the prompt context, not in its training.

That's the key insight.


===== WHAT ARE EMBEDDINGS? =====

[SHOW: Diagram 4a - Embedding Space Clustering]

Let me explain what "embedding" means.

When we embed text, we convert it to a vector—a list of numbers that captures its meaning.

Here's the magic: words with similar meanings end up as similar vectors.

Apple and banana are close together. Chicago and Detroit are close. Dog and cat are close.

[SHOW: Diagram 4b - Query Vector Finding Matches]

When someone asks a question, it gets embedded too.

A question about fruits lands near the fruit cluster. RAG finds the nearest chunks and retrieves them.

That's how the system knows which pieces of your documents are relevant to the question.


===== WHY DOES RAG EXIST? =====

[SHOW: Diagram 2 - Context Window Timeline]

RAG was developed when context windows were tiny—4K or 8K tokens. You couldn't fit a single long document in the prompt.

Today, context windows are much larger. So do we still need RAG?

For now—yes. We still hit context limits on real codebases, and retrieval is often faster and cheaper than stuffing everything into the prompt.

But this is worth watching. The constraint that created RAG is shrinking.

===== CODE WALKTHROUGH =====

[SHOW: Side-by-side of all three: document_loader.py, DocumentLoaderService.java, DocumentLoader.java]

All three versions follow the same six-step flow. The differences are in the wiring.

For chunking, Python uses RecursiveCharacterTextSplitter—it breaks on paragraph boundaries. Spring AI uses TokenTextSplitter—it counts tokens. LangChain4j uses recursive splitting with character overlap.

Different strategies, same goal: chunks small enough for a prompt, large enough to be useful.

[SHOW: Diagram 3 - RAG Retrieval Flow]

[SHOW: rag_chain.py, RagService.java (Spring AI), RagService.java (LangChain4j)]

For retrieval and generation, Python chains components with LangChain's expression language. Spring AI uses ChatClient with a QuestionAnswerAdvisor. LangChain4j uses AiServices—you define a Java interface and it generates a proxy.

Three APIs, same pattern.


===== THE PROMPT TEMPLATE =====

One thing students often overlook: the prompt template matters.

All three frameworks provide sensible defaults that say: answer based ONLY on this context. If the answer isn't there, say so.

This prevents hallucination—the model won't make things up because we've constrained it.

You CAN customize these prompts, but the defaults work well for most use cases.


===== BONUS: PERSISTENT STORAGE =====

[SHOW: Supabase dashboard]

The main branch uses in-memory storage—fine for demos, but your vectors disappear when the app stops.

On a separate branch, I've added Supabase—PostgreSQL with the pgvector extension.

Here's what's interesting: all three implementations connect to the same database and share the same table.

[SHOW: Schema diagram]

I aligned the schemas—same table name, same embedding model, same metadata format.

Load a document from Spring AI, query it from LangChain4j or Python. It just works.

This took some deliberate configuration. Same database doesn't mean automatic interoperability—you have to align on table structure, embedding dimensions, and metadata format.

But once you do, cross-language interop is a powerful capability.


===== WHEN TO USE RAG =====

Quick decision guide.

Use RAG when your data changes frequently—no retraining needed.

Use RAG when you need to cite sources—you know exactly what the model saw.

Use RAG when data is private—it never leaves your infrastructure.

What about fine-tuning?

Fine-tuning is expensive, and when you change the model's weights, it's not clear how that affects other responses.

RAG is transparent—you can see exactly what context the model received. If an answer is wrong, check which chunks were retrieved and debug from there.

For most enterprise use cases, RAG is the right starting point.


===== WRAP-UP =====

Let's recap.

RAG lets you give an LLM access to your private data without retraining it.

Load, chunk, embed, store, retrieve, generate.

The question becomes a vector. The nearest chunks become context. The LLM generates an answer.
